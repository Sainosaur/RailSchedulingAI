Note on DTZ vs distance_available
----------------------------------
All get_safe_action tests pass DTZ (Distance-to-Zone) as the raw sensor input, not distance_available.
DTZ is a physical measurement derived from balise position and train odometry — it is the primitive input the train natively knows.
distance_available = DTZ + (aspect * SH) is computed internally by the VL.
If the caller passed distance_available, they would need to hardcode the aspect-to-blocks mapping
themselves, leaking VL internal logic. The VL owns this computation.
Each test comment includes the resulting distance_available for mathematical clarity.

Note on overridden vs safe_a
------------------------------
`overridden` is a boolean: did the VL intervene?
    False = the AI's proposed action was safe, returned unchanged.
    True  = the VL detected a predicted violation and computed a correction.
`safe_a` is the specific correction value, computed by SUVAT when overridden=True:
    a_needed = -u² / (2 * distance_available)
    Clamped to [EMERGENCY_DECEL, SERVICE_DECEL] = [-1.0, -0.5].

These are two separate assertions. `overridden=True` does NOT mean `safe_a == -1.0`.
Emergency braking only occurs when a_needed is more severe than -1.0 m/s²
(i.e., the train is so close and fast that even service braking is insufficient).
For mild violations (large distance, moderate speed), safe_a will be SERVICE_DECEL (-0.5).

12. test_clamp_extreme_action
Input: proposed_a=-5.0, aspect=3, x=1000, u=10, dtz=300.
      distance_available = 1237.5m.
Flow: Hardware clamp: clamped_a = max(-1.0, min(0.5, -5.0)) = -1.0. was_hardware_clamped=True.
      Layer 2 runs on -1.0: train decelerates safely well before boundary. is_safe=True.
      Since is_safe=True but was_hardware_clamped=True:
          log_override(proposed_a=-5.0, clamped_a=-1.0, 'Hardware_Limit_Clamp').
          return (-1.0, True).
Assertion: overridden=True, safe=-1.0.
Insight: overridden=True whenever the VL returns a value different from proposed_a,
regardless of the reason (hardware limit or safety violation). The distinction is
captured in the constraint_id logged: 'Hardware_Limit_Clamp' vs 'Aspect_Spatial_Violation'.
Previously marked overridden=False, which was wrong — the VL replaced -5.0 with -1.0.

13. test_override_segment_overspeed
Input: proposed_a=+0.5, aspect=3 (Green), x=14900, u=20, dtz=300.
      distance_available = 300 + 3*312.5 = 1237.5m. boundary_x = 16137.5m.
Flow: Layer 2, t=8s: x_proj=15076 (in S2). v=24 > S2 limit=16.67 → S2_Limit violation.
      Layer 3: a_needed = -(400)/(2475) ≈ -0.1616 m/s².
              Clamped: max(-1.0, min(0.0, -0.1616)) = -0.1616.
Assertion: overridden=True, safe ≈ -0.1616 (precise SUVAT value).

Why -0.1616 and not SERVICE_DECEL (-0.5):
The previous design clamped safe_a to at least SERVICE_DECEL, meaning even mild violations
got a -0.5 correction. This was unnecessarily aggressive. If a_needed=-0.1616 stops the
train in time, that IS the safe deceleration — applying more braking than needed harms the
AI's reward signal and creates uncomfortable speed changes. The VL returns the minimum
correction required, not a fixed floor. This preserves the gradient the PPO needs to learn
smooth deceleration ahead of speed limit transitions.
