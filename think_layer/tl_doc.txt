THINK LAYER — ARCHITECTURE & DESIGN JUSTIFICATION
===================================================
File: think_layer/  (agent.py, trainer.py, evaluate.py, config.py)


------------------------------------------------------------------
1. WHAT THE THINK LAYER IS
------------------------------------------------------------------
The Think Layer (TL) is the decision-making brain of the AI train.
It is a PPO (Proximal Policy Optimisation) reinforcement learning agent
trained using Stable-Baselines3.  Every second, it receives a snapshot
of the train's current state (speed, position, signal aspect, headway,
distance to next station, etc.) and outputs a single continuous value:
the acceleration to apply over the next second.

The TL does not make safety decisions.  That is the Validation Layer's
job.  The TL only decides *how to drive efficiently* within whatever
safe boundaries the Validation Layer permits.


------------------------------------------------------------------
2. WHY PPO
------------------------------------------------------------------
PPO is a policy-gradient reinforcement learning algorithm suited to
continuous control problems — exactly what train driving is.  The
action space (a single continuous acceleration value) maps directly
onto what a driver does: apply more or less throttle/brake.

Alternative approaches (e.g. rule-based PID controllers, optimal
control) require full knowledge of the track geometry, speed limits,
and timetable to be encoded manually.  PPO learns these implicitly
from the reward signal during training, making it more adaptable to
changing conditions and easier to retrain when track data changes.


------------------------------------------------------------------
3. WHAT THE THINK LAYER OPTIMISES
------------------------------------------------------------------
The TL is trained to optimise four operational objectives.  Safety is
explicitly excluded — it is handled entirely by the Validation Layer
before any action reaches the physics engine.

  A. JERK MINIMISATION
     Abrupt changes in acceleration (sudden braking, sudden throttle)
     cause passenger discomfort and mechanical wear.  The reward
     function penalises the magnitude of step-to-step acceleration
     changes, training the agent to produce smooth, gradual speed
     transitions.

  B. MAXIMUM VELOCITY EFFICIENCY
     The agent is rewarded for maintaining speed close to the
     trapezoidal "ideal" curve — fast enough to make good time, slow
     enough to brake comfortably before the next station.  It is
     penalised quadratically for overspeeding and linearly for
     travelling significantly below the comfortable target speed.

  C. ENERGY EFFICIENCY
     Traction (applying positive throttle) costs energy.  Coasting and
     braking are free.  The reward function applies a small continuous
     penalty for every unit of traction used, training the agent to
     coast where possible and avoid unnecessary acceleration bursts.

  D. PUNCTUALITY
     On arrival at each station, the agent is rewarded for arriving
     within a tolerance window of the scheduled time, and penalised
     proportionally for every second outside that window.
     NOTE: This component is currently inactive — the environment does
     not yet supply timetable data.  It is wired up and ready to
     enable when a timetable is added.


------------------------------------------------------------------
4. DOES THE PPO NEED TO KNOW WHERE ALL OTHER TRAINS ARE?
------------------------------------------------------------------
No — and it would be the wrong design to give it that information.

The on-train PPO is a driver, not a dispatcher.  Its job is to take
one train from A to B efficiently and smoothly.  A real train driver
does not need to know the positions of 49 other trains on the line.
They respond to the signal directly ahead of them.  That is exactly
what this system does: the agent sees the signal aspect (derived from
the distance to the lead train) and reacts accordingly.

The "avalanche effect" — where one late train causes cascading delays
down the line — is a *scheduling* problem, not a *driving* problem.
Giving each driver the global train map does not fix cascading delays;
it just asks the wrong agent to solve the wrong problem.

The architecturally correct solution to delay propagation is a
centralised fleet scheduler that has global visibility and issues
speed-target adjustments to individual trains.  This is how real
traffic management centres work.  However, this is entirely out of
scope for this project.


------------------------------------------------------------------
5. WHY MULTI-TRAIN SCHEDULING IS OUT OF SCOPE
------------------------------------------------------------------
This project's focus is single-train driving efficiency.  The four
objectives above (jerk, velocity, energy, punctuality) are all
properties of one train's journey.  None of them require knowledge of
other trains' positions.

Multi-train scheduling is a fundamentally different problem class:
it requires a multi-agent architecture, global state, and a different
reward structure centred on network-level metrics (total delay, total
throughput) rather than per-train efficiency.  Solving it well is
an independent research problem.

The convoy model (one AI train following one lead train) is sufficient
to train all four efficiency objectives.  The lead train's station
stops create natural dynamic headway challenges that force the agent
to learn smooth approach and departure behaviour — the exact skills
that would be useful in a real dense-traffic scenario — without the
architectural complexity of a multi-agent system.

Scheduling is deferred to a future phase and is explicitly not a
design requirement of the current system.

6. EDGE DEPLOYMENT — RUNNING WITHOUT CLOUD OR INTERNET
------------------------------------------------------------------
The Think Layer can run entirely offline on embedded hardware once
training is complete.  No internet connection is required at inference
time.

HOW IT WORKS AT DEPLOYMENT:

  The trained model is saved as a small file (roughly 200 KB for a
  two-hidden-layer network).  At startup the on-board computer loads
  this file and uses it to make driving decisions locally.  The
  computation is a simple forward pass through a small neural network —
  fast enough to run in real time on a low-power device.

  The Validation Layer is also fully self-contained.  It uses fixed
  track geometry data and pure mathematics.  No external calls.

  The signal aspect the agent reacts to (Red / Yellow / Green) comes
  from the ETCS Movement Authority issued by the Radio Block Centre
  (RBC) over the train's existing GSM-R radio link.  This is the same
  data feed trains already receive today — no new infrastructure is
  needed.

WHAT NEEDS TO BE FIXED BEFORE EDGE DEPLOYMENT:

  The graph builder (graph/utils/station_detail.py) currently calls
  two external internet APIs at startup to fetch station elevation
  data.  This must be replaced with a locally stored data file before
  the system can run offline.  This is an infrastructure fix in the
  graph layer, not the think layer.

  Everything else — the PPO model, the Validation Layer, the reward
  computation, the physics — is already self-contained and offline-
  capable.

SUMMARY: Edge deployment is viable.  The only blocker is one file in
the graph layer that fetches data from the internet.  The think layer
and validation layer require no changes for offline operation.


------------------------------------------------------------------
7. PIPELINE OVERVIEW
------------------------------------------------------------------

  config.py   — All hyperparameters, paths, and toggles in one place.
                Change training settings here; nothing else needs editing.

  agent.py    — Builds the Gymnasium environment and wraps it for SB3.
                Applies VecNormalize for observation and reward scaling.
                Constructs the PPO model with the network architecture
                from config.

  trainer.py  — Runs the training loop.  Sets up checkpointing (saves
                a model snapshot every N steps) and a separate frozen
                evaluation environment to monitor progress without
                contaminating training stats.

  evaluate.py — Loads a saved model and runs evaluation episodes.
                Prints a summary (reward, override rate, stations
                visited) and saves a per-step CSV for analysis plots.

  train.py    — Entry point.  Run with:
                    python -m think_layer.train
